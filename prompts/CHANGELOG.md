# Prompt iteration log

Everything below is an observation from a real run, not a prediction. Raw model output
for every attempt — including rejected drafts — is preserved in `output/attempts/`. Both
versions are reproducible: `pnpm brief -- --prompt v1` / `pnpm brief`.

## v1 — the naive prompt

`prompt-v1.md` handed the model the facts JSON and asked for "a briefing an executive can
read in 5 minutes" covering sales, trends, stock risks, and reorder reasoning. No
structure, no rules about arithmetic.

## What actually happened when v1 ran

Attempt 1 (`output/attempts/v1-attempt-1.md`) failed validation. The honest scorecard:

1. **It invented its own structure.** Seven numbered sections with its own names — a
   perfectly reasonable document, but a *different* document every run, which the
   validation gate cannot check. All six required-section checks failed, and because the
   gate couldn't locate a reorder section, the ranking checks failed with it. The retry
   (with the failure list appended) produced a conforming attempt 2 that passed — so the
   retry loop works, but relying on it doubles cost and latency. Structure belongs in the
   prompt, not in the retry.
2. **It did its own arithmetic.** "Up **8.3%** from February", "~**$97,664/month** of
   combined exposure", per-row cover-gap columns, "less than half the portfolio average".
   I hand-checked these — all correct, impressively — but *unverified-correct*, which is
   the exact failure mode this architecture exists to remove. The gate cannot audit prose
   arithmetic; the only fix is upstream.
3. **It ran long.** ~1,100 words plus nine tables of its own, several duplicating the
   machine-generated appendix. Dense reading against a 5-minute bar.
4. **It exposed a bug in my validator, not just in itself.** The gate flagged
   "the Bioactive Blend launch" as an invented SKU — a false positive on legitimate
   collective prose. Fixed in `src/validate-brief.ts` (capitalized-variant matching) with
   a regression test, and the same pass added a real missing check: invented *size*
   variants of real strengths ("MGO 850+ 100g") previously slipped through.

**What v1 did well — and what I got wrong about it.** My first draft of this log, written
before running v1, predicted it would bury the decision mid-document and miss the planted
tensions. The run disproved both: attempt 1 led its executive summary with "the one thing
to action this week" and surfaced the Propolis phase-out tension *and* the MGO 100+
Amazon dip — because both live in the facts JSON as flags, which is where they should
live. It also produced genuinely sharp cross-SKU reads the facts don't state directly
(growth rising with potency, 500g outpacing 250g in every matched pair, Amazon becoming
the premium-discovery channel). That draft of this log was deleted and rewritten from
the evidence — the same rule the pipeline enforces on the model applies to me.

## v2 — what changed and why

Each rule traces to a v1 observation:

- **Fixed six-section structure** ← attempt 1's invented layout (makes output validatable
  and enforces the 5-minute read).
- **"Use ONLY the numbers in the JSON", with executive rounding** ← the self-computed
  8.3% and $97,664.
- **Consequence-first reasoning required per recommendation** ← keeping v1's genuine
  strength, but as a rule instead of luck.
- **Name both tensions explicitly** ← not because v1 missed them (it didn't) but because
  required content should be deterministic, not dependent on the model noticing.
- **No model-written appendix** ← v1's nine tables; the appendix is generated by code.

## What v2's first run exposed

v2 run 1 passed validation on attempt 1 — and still did one sum: "roughly $98K a month"
for the four REORDER_NOW exposures (`output/attempts/v2-run1-attempt-1.md`). Correct
(97,665), but the gate can't verify model arithmetic, and rule 1 said *use* the numbers,
not *derive* them. The fix was upstream, not in the prompt: the facts JSON now carries
`totals.reorderNowExposureUsdPerMonth` pre-summed, and the briefing was regenerated. If
the narrative needs a number, the number must exist in the facts.

## The final run, and what verification still found

The committed `output/sop-briefing.md` (v2, second run) passed validation on attempt 1,
cites the exposure total from the facts, and hand-checks clean — including its
"without the inbound orders" counterfactuals, which come from `runwayWithoutOrderMonths`
in the facts. Two loose unit conversions survive: "inside six weeks" for a 1.42-month
runway (≈6.1 weeks) and "nine-week-old launch" for mid-January → end of March (~10–11
weeks). Both are qualitative, neither changes a decision, and I don't hand-edit
generated output — so they're recorded here instead of silently fixed.

## Where the AI helped, where it was wrong, what was changed manually

- **Helped:** v1's cross-SKU inference and v2's consequence-first narrative are better
  than a template could produce; Claude Code built the engine, tests, and validator
  alongside me throughout.
- **Wrong:** v1's unverifiable arithmetic; the AI-written validator's own false positive
  (caught only by running it against real output); v2 run 1's self-summed total; and my
  own pre-run assumptions about v1's failure modes.
- **Manual:** all math, ranking policy (urgency tier first, revenue within tier), and
  special-rule handling moved into tested TypeScript before any prompt ran; the
  validation gate's rules and both of its fixes; the facts-contract change that ended
  model arithmetic.
